# Agent Team Design Patterns

> OpenCode Harness 메타 스킬 참조 문서 — 에이전트 팀 아키텍처 패턴 카탈로그

---

## 실행 모드: 에이전트 팀 vs 서브 에이전트

에이전트 팀을 구성할 때는 두 가지 실행 모드 중 하나를 선택한다.

### 에이전트 팀 (Agent Team) — 기본 모드

```
┌─────────────────────────────────────────────────────┐
│  Orchestrator                                       │
│                                                     │
│  TeamCreate("analysts")                             │
│  SendMessage("analysts", "분석 시작해")              │
│  TaskCreate("analysts", { task: "report" })         │
│                                                     │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐         │
│  │ Agent A  │◄─┤ Agent B  │◄─┤ Agent C  │         │
│  │          │──►│          │──►│          │         │
│  └──────────┘  └──────────┘  └──────────┘         │
│       에이전트 간 자유로운 통신 가능                    │
└─────────────────────────────────────────────────────┘
```

- `TeamCreate(name, agents)`로 팀을 생성하고 `SendMessage`/`TaskCreate`로 작업 지시
- 팀 내 에이전트들은 **자유롭게 서로 통신**하며 정보 공유 가능
- 협업이 필요한 복잡한 작업에 적합 (브레인스토밍, 코드 리뷰, 공동 분석)
- **단점**: 통신 오버헤드, 에이전트 간 혼선 가능성

### 서브 에이전트 (Sub-agent) — 직접 호출 모드

```
┌──────────────────────────────────────────┐
│  Orchestrator                             │
│                                           │
│  agent("분석가") ← 직접 호출 (call_omo_agent)  │
│  agent("검토자") ← 직접 호출 (call_omo_agent)  │
│                                           │
│  ┌──────────┐    ┌──────────┐            │
│  │ Agent A  │    │ Agent B  │            │
│  │ (격리)   │    │ (격리)   │            │
│  └──────────┘    └──────────┘            │
│    에이전트 간 통신 없음, 오케스트레이터만 연결    │
└──────────────────────────────────────────┘
```

- `call_omo_agent()` 등 Agent tool을 통해 직접 호출
- 각 에이전트는 **격리되어 실행**, 서로 통신하지 않음
- 오케스트레이터가 모든 중개를 담당
- **장점**: 단순함, 예측 가능, 디버깅 용이
- **단점**: 에이전트 간 협업 불가, 오케스트레이터 병목

### 결정 트리

```
작업이 여러 에이전트 간 협업이 필요한가?
├── YES → 에이전트가 서로 자유롭게 소통해야 하는가?
│   ├── YES → Agent Team 모드
│   └── NO  → Sub-agent 모드 (오케스트레이터가 중개)
└── NO  → 단일 에이전트로 충분
```

## 에이전트 팀 아키텍처 유형

### 1. 파이프라인 (Pipeline)

```
  [입력] ──► [Agent A] ──► [Agent B] ──► [Agent C] ──► [출력]
               단계 1          단계 2          단계 3
```

**설명**: 각 에이전트가 순차적으로 작업을 수행하며, 이전 단계의 출력이 다음 단계의 입력이 된다. 의존성이 있는 작업에 가장 기본적인 패턴.

**사용 시기**:
- 작업 단계 간 순서 의존성이 명확할 때
- 각 단계를 서로 다른 전문성이 필요한 작업으로 분리할 수 있을 때
- 예: 요구사항 분석 → 아키텍처 설계 → 구현 → 테스트

**예시**:
```
요구사항 분석 Agent → API 설계 Agent → 구현 Agent → 테스트 Agent
```

**주의사항**:
- 전체 처리 시간 = 각 단계 처리 시간의 합 (병렬화 불가)
- 한 단계 실패 시 전체 파이프라인 중단
- 각 단계의 출력 형식을 표준화해야 함

### 2. 팬아웃/팬인 (Fan-out/Fan-in)

```
                  ┌─► [Agent A1] ─┐
                  │               │
  [오케스트레이터] ──┼─► [Agent A2] ──┼─► [집계 Agent]
                  │               │
                  └─► [Agent A3] ─┘
                   병렬 처리         결과 취합
```

**설명**: 오케스트레이터가 작업을 여러 독립적인 하위 작업으로 분할하여 병렬 실행하고, 모든 결과를 집계 에이전트가 취합한다.

**사용 시기**:
- 독립적으로 처리 가능한 여러 하위 작업이 있을 때
- 다양한 관점이나 접근 방식이 필요할 때
- 처리 시간을 단축해야 할 때

**예시**:
```
코드 리뷰: 여러 파일을 각각 다른 리뷰어에게 병렬 할당 → 결과 취합
문서 생성: 개요, 상세, 예제를 각각 생성 → 하나의 문서로 통합
```

**주의사항**:
- 에이전트 수 증가에 따른 맥락 창 소비
- 집계 단계의 병목 가능성
- 하위 작업 간 충돌이나 중복 처리 방지 필요

---

### 3. 전문가 풀 (Expert Pool)

```
                    ┌── [보안 전문가] ──┐
                    │                    │
  [요청] ──► [라우터] ──┼── [성능 전문가] ──┼──► [출력]
                    │                    │
                    └── [UX 전문가] ────┘
                   컨텍스트 기반 선택         응답 통합
```

**설명**: 입력 컨텍스트에 따라 적절한 전문가 에이전트를 선택적으로 호출한다. 모든 에이전트가 항상 실행되는 것은 아니다.

**사용 시기**:
- 작업 성격에 따라 필요한 전문 분야가 다를 때
- 모든 전문가를 항상 실행하면 비용이 과도할 때
- 입력 분석 후 동적으로 라우팅 결정을 내려야 할 때

**예시**:
```
PR 리뷰: 변경된 파일의 종류에 따라 프론트엔드/백엔드/인프라 전문가 선택 호출
버그 트라이지: 버그 유형(UI/로직/성능)에 따라 적절한 분석가 호출
```

**주의사항**:
- 라우터의 분류 정확도가 전체 품질 결정
- 전문가 간 지식 공유 부재로 일관성 문제 가능
- 예상치 못한 입력 조합에서 누락 발생 가능

---

### 4. 생성-검증 (Producer-Reviewer)

```
  [요청] ──► [생성 Agent] ──► [검증 Agent] ──► {통과} ──► [출력]
                                    │
                                    └── {실패} ──► [생성 Agent] (재시도)
```

**설명**: 생성 에이전트가 결과물을 만들고, 검증 에이전트가 품질을 확인한다. 검증 실패 시 생성 단계로 피드백 루프가 발생한다.

**사용 시기**:
- 품질이 중요한 결과물이 필요할 때 (코드, 문서, 설계)
- 객관적인 검증 기준을 정의할 수 있을 때
- 단일 에이전트의 자기 검증 한계를 보완해야 할 때

**예시**:
```
코드 생성 → 테스트 코드 검증 (통과 시 출력, 실패 시 수정)
문서 생성 → 사실 확인 + 일관성 검증
아키텍처 설계 → 제약 조건 충족 검증
```

**주의사항**:
- 최대 재시도 횟수 설정 필요 (무한 루프 방지)
- 검증 기준이 너무 엄격하면 과도한 재시도 발생
- 검증 에이전트에도 충분한 컨텍스트 제공 필요

---

### 5. 감독자 (Supervisor)

```
  [요청] ──► [감독자 Agent] ──► 작업 분배 ──► [Agent A]
                    │                          │
                    │                    [Agent B]
                    │                          │
                    └── 결과 수집 ◄────── [Agent C]
                    
                    감독자: 작업 분배 + 진행 추적 + 결과 통합
```

**설명**: 중앙 감독자 에이전트가 전체 워크플로우를 관리하고, 작업을 동적으로 분배하며, 진행 상황을 추적하고 최종 결과를 통합한다.

**사용 시기**:
- 작업이 동적으로 분화되거나 우선순위가 변경될 때
- 여러 작업을 조율하고 진행 상황을 추적해야 할 때
- 에이전트 간 충돌이나 중복을 관리해야 할 때

**예시**:
```
소프트웨어 프로젝트 관리: 감독자가 이슈 트래킹 + 작업 할당 + 일정 관리
리서치 프로젝트: 감독자가 가설 수립 → 여러 연구원에게 조사 분배 → 결과 종합
```

**주의사항**:
- 감독자가 단일 장애점 (SPOF)이 됨
- 감독자의 맥락 창이 전체 병목이 될 수 있음
- 감독자에게 도메인 지식과 메타 인지 능력이 모두 필요

---

### 6. 계층적 위임 (Hierarchical Delegation)

```
  [최상위 Agent]
       │
       ├── [중간 관리자 A]
       │       ├── [실무자 A1]
       │       └── [실무자 A2]
       │
       └── [중간 관리자 B]
               ├── [실무자 B1]
               └── [실무자 B2]
```

**설명**: 상위 에이전트가 하위 에이전트에게 작업을 재귀적으로 위임한다. 각 계층은 자신의 책임 범위 내에서만 작업을 처리한다.

**사용 시기**:
- 작업 규모가 매우 크고 자연스러운 계층 구조로 분해될 때
- 각 하위 도메인이 독립적인 책임 영역을 가질 때
- 조직 구조(리드 → 팀 리드 → 개발자)를 모방할 때

**예시**:
```
시스템 설계: 설계 리드 → 서브시스템 리드 → 각 컴포넌트 담당
문서화: 문서 리드 → 챕터 작가 → 섹션 작성자
```

**주의사항**:
- 계층이 깊어질수록 통신 지연과 맥락 손실 증가 (일반적으로 3단계 이하 권장)
- 상위 계층의 의사결정 오류가 하위로 전파됨
- 각 계층의 인터페이스(입출력 형식)를 명확히 정의해야 함

## 복합 패턴

실제 워크플로우는 단일 패턴으로 해결되지 않는 경우가 많다. 다음과 같은 복합 패턴을 고려한다.

### 팬아웃 + 생성-검증

```
                ┌─ [생성 A] → [검증 A] ─┐
  [요청] ──► 팬아웃 ──┼─ [생성 B] → [검증 B] ──┼─► 집계 → 출력
                └─ [생성 C] → [검증 C] ─┘
```

각 병렬 작업에 자체 검증 단계를 포함. 품질이 중요한 병렬 작업에 적합.

### 파이프라인 + 팬아웃

```
  [단계 1] ──► [단계 2] ──► 팬아웃 ──► [단계 3a] ──┐
                              │                   │
                              ├── [단계 3b] ──────┼──► [단계 4]
                              │                   │
                              └── [단계 3c] ──────┘
```

일부 단계는 순차적이지만, 병렬화 가능한 단계에서 팬아웃.

### 감독자 + 전문가 풀

```
  [감독자] ── 동적 라우팅 ──► [전문가 풀]
       │                        │
       │                   필요시 전문가 선택 호출
       │                        │
       └── 진행 추적 ────── 상황 보고
```

감독자가 동적으로 필요한 전문가를 선택하여 호출하고 진행을 추적.

## 에이전트 타입 선택

### 내장 타입

| 타입 | 용도 | 특징 |
|---|---|---|
| `explore` | 탐색, 리서치, 정보 수집 | 웹 검색, 파일 읽기 등 정보 수집에 특화 |
| `librarian` | 코드베이스 분석, 문서 검색 | 대규모 코드베이스 이해에 최적화 |
| `oracle` | 검증, 품질 평가, 감리 | 객관적 기준으로 결과물 평가 |
| `build` | 일반 구현, 코드 생성 | 범용 작업 에이전트 |
| `multimodal-looker` | 이미지/미디어 분석 | 시각적 콘텐츠 분석 |

### 커스텀 타입

`.agents/` 디렉토리에 마크다운 파일로 정의:

```
.agents/
├── senior-frontend.agent.md
├── terraform-expert.agent.md
└── security-reviewer.agent.md
```

### 선택 기준

| 조건 | 권장 타입 |
|---|---|
| 웹 검색/정보 수집이 주요 작업 | `explore` |
| 기존 코드베이스 이해가 필요 | `librarian` |
| 결과물의 품질 검증 | `oracle` |
| 특정 기술/도메인 전문성 필요 | 커스텀 에이전트 |
| 일반적인 생성/구현 | `build` 또는 커스텀 |

## 에이전트 정의 구조

에이전트 정의 파일 (`.agents/*.agent.md`) 템플릿:

```markdown
# Agent Name

Agent system prompt content.

## Instructions

Detailed behavioral instructions for the agent.

## Tools

- Tool name and description
- Permissions and constraints

## Context

- Required context format
- Input/output expectations

## Examples

- Example interactions
- Expected output format
```

### 필수 섹션

- **역할 정의**: 에이전트의 전문 분야와 책임을 명확히 기술
- **지침**: 행동 패턴, 의사결정 기준, 제약 사항
- **도구**: 사용 가능한 도구 목록과 사용 조건
- **맥락**: 필요한 입력 정보와 출력 형식
- **예시**: 구체적인 상호작용 예시 (선택 사항이지만 권장)

## 에이전트 분리 기준

언제 에이전트를 분리하고 언제 통합할지 결정하는 기준:

| 기준 | 분리 (Separation) | 통합 (Integration) |
|---|---|---|
| **전문성** | 각각 고유한 도메인 지식 필요 | 단일 도메인 내 다양한 작업 |
| **병렬성** | 독립적으로 실행 가능한 작업 | 순차적 의존성이 있는 작업 |
| **맥락** | 각각 다른 맥락/데이터셋 필요 | 동일한 맥락 공유 가능 |
| **재사용성** | 다른 워크플로우에서 재사용 가능 | 해당 워크플로우에 한정된 역할 |
| **복잡도** | 각 역할이 단순하고 명확함 | 에이전트 간 통신 오버헤드가 큼 |
| **비용** | LLM 토큰 비용 분산 가능 | 단일 에이전트가 더 경제적 |

### 분리 결정 질문

1. 이 작업을 분리하면 어떤 이점이 있는가? (전문성, 병렬성)
2. 분리로 인한 통신 오버헤드가 이점보다 적은가?
3. 각 에이전트가 독립적으로 유용한가? (재사용성)
4. 분리된 에이전트를 관리할 맥락 창이 충분한가?

## 스킬 vs 에이전트 구분

| 기준 | 스킬 (Skill) | 에이전트 (Agent) |
|---|---|---|
| **본질** | 절차적 지식 — "어떻게 할지" | 전문가 페르소나 — "누가 할지" |
| **내용** | 단계별 가이드, 체크리스트, 규칙 | 역할 정의, 의사결정 권한, 행동 패턴 |
| **범위** | 좁은 작업 단위 (lint, 테스트, 배포) | 넓은 책임 영역 (분석, 설계, 검증) |
| **호출 방식** | `skill("name")` 으로 로드 | `call_omo_agent()` 또는 팀 멤버로 참여 |
| **상태** | 무상태 — 매번 동일한 지침 제공 | 유상태 — 대화 맥락 유지 가능 |
| **구성 위치** | OpenCode config 또는 `.agents/skills/` | `.agents/*.agent.md` |
| **사용 예** | `terraform-style-guide`, `nestjs-best-practices` | `senior-frontend.agent.md`, `security-reviewer.agent.md` |
| **조합** | 하나의 에이전트가 여러 스킬 로드 가능 | 여러 에이전트가 동일한 스킬 공유 가능 |

### 실무 지침

- **스킬 우선**: 반복적인 절차는 스킬로 정의 (e.g., "릴리즈 절차", "코드 리뷰 체크리스트")
- **에이전트 필요 조건**: 판단력, 맥락 이해, 능동적 의사결정이 필요할 때
- **혼용**: 에이전트 정의 내에서 `load_skills` 파라미터로 관련 스킬 참조

```markdown
# .agents/terraform-expert.agent.md 예시 (내부 참조)
load_skills: ["terraform-style-guide"]
→ 이 에이전트는 Terraform 배포 시 자동으로 스타일 가이드 스킬을 로드함
```
