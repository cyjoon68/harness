# Deep Mode — Ouroboros 방법론

## 개요

Deep mode는 Ouroboros (https://github.com/Q00/ouroboros) 에서 영감을 받은
사양-우선(specification-first) 접근법이다. 에이전트 팀이나 스킬을 생성하기 전에,
소크라테스식 질문(Socratic questioning)과 온톨로지 분석(ontology analysis)을 통해
표면 요구사항 아래 숨겨진 가정과 전제를 드러낸다.

Deep mode의 핵심 원칙은 간단하다:

> 무언가를 만들기 전에, 그것이 무엇인지 정확히 알아야 한다.

이 원칙은 소프트웨어 공학의 가장 오래된 교훈 — "요구사항을 먼저 이해하라" — 를
극단적으로 밀어붙인다. 일반적인 요구사항 수집은 "무엇을 만들까?"에 집중하지만
deep mode는 "내가 진짜로 원하는 게 무엇일까?"라는 근본적인 물음에서 시작한다.

## 핵심 철학: Wonder에서 온톨로지로

### Wonder ("내가 원하는 게 뭐지?")

모든 창조는 Wonder에서 시작한다. Wonder은 막연하고, 모호하며, 아직 형태가 없다.
"채팅 앱이 필요해" — 이 말은 Wonder의 전형적인 표현이다. 표면적으로는 명확해
보이지만, 실제로는 수많은 해석의 여지가 있다.

- 실시간인가? 비동기인가?
- 1:1인가? 그룹인가?
- 영구 저장이 필요한가? 휘발성이어도 되는가?
- 누가 운영하는가? 무슨 프로토콜을 쓰는가?
- 어떤 가정을 하고 있는가?

Wonder은 창조의 연료이지만, 그 자체로는 실행 가능한 사양이 아니다.

### 온톨로지 ("내가 원하는 게 정확히 뭐지?")

온톨로지는 Wonder에서 정밀함으로의 이동이다. 존재의 본질을 묻는 철학적 질문을
소프트웨어 설계에 적용한다:

- 이 개념의 본질은 무엇인가?
- 이것은 다른 무엇과 어떻게 다른가?
- 이것은 다른 무엇과 어떻게 연결되는가?
- 어떤 경계 조건에서 이것이 더 이상 유효하지 않은가?

온톨로지 수렴은 모든 참여자가 동일한 개념적 모델을 공유할 때까지 질문을 반복하는
과정이다. 이 지점에 도달하면, 모호성(ambiguity)이 임계치 이하로 떨어지고
비로소 실행 단계로 넘어갈 수 있다.

### 표면 요구사항은 깊은 가정을 숨긴다

```
요청: "로그인이 필요해요"
  └─ 가정 1: 사용자 식별이 필요하다
      └─ 가정 1.1: 사용자는 인간이다
      └─ 가정 1.2: 사용자는 고유하다
  └─ 가정 2: 인증이 필요하다
      └─ 가정 2.1: 비밀번호가 필요하다
          └─ 가정 2.1.1: 사용자가 비밀번호를 기억할 수 있다
          └─ 가정 2.1.2: 비밀번호가 충분히 안전하다
      └─ 가정 2.2: 세션이 필요하다
  └─ 가정 3: 권한 부여가 필요하다
      └─ 가정 3.1: 역할(role) 개념이 존재한다
```

질문의 깊이는 표면 요구사항 아래에 몇 겹의 가정이 있는지 드러낸다. 좋은 질문은
더 깊은 질문을 낳는다 — 이것이 deep mode가 순환적(circular)인 이유다.

### 좋은 질문이 더 깊은 질문을 낳는다

Socratic Interviewer의 역할은 이 질문 사슬을 끝까지 따라가는 것이다. 각 답변은
새로운 질문을 열고, 그 질문은 더 정밀한 온톨로지를 요구한다. 이 과정은
다음 조건 중 하나가 충족될 때까지 계속된다:

1. 질문이 더 이상 존재하지 않는다 (온톨로지 완전)
2. 모든 답변이 모순 없이 일관된다 (온톨로지 일관)
3. 모호성 점수가 임계치 이하로 떨어진다 (온톨로지 수렴)

## Double Diamond 구조

Deep mode의 실행 구조는 이중 마름모(Double Diamond) 디자인 프로세스를 따른다.
첫 번째 마름모는 Socratic (질문 → 온톨로지), 두 번째 마름모는 Practical (설계 → 전달)이다.

```text
    ◇ Wonder         ◇ 설계
   ╱  (넓히기)       ╱  (넓히기)
  ╱    탐색         ╱    창조
 ╱                 ╱
◆ ──────────── ◆ ──────────── ◆
 ╲                 ╲
  ╲    정의         ╲    전달
   ╲  (좁히기)      ╲  (좁히기)
    ◇ 온톨로지       ◇ 평가
```

### 첫 번째 마름모: Socratic Phase

**1. 탐색 (Discover) — 확산**

Wonder에서 시작한다. Socratic Interviewer가 질문을 던지고, 모든 가능성을 열어둔다.
이 단계에서는 판단하지 않고 최대한 많은 관점을 수집한다.

- "왜 이것이 필요한가?"
- "누가 이것을 사용할 것인가?"
- "이것이 해결하는 근본 문제는 무엇인가?"
- "이것이 존재하지 않는다면 무슨 일이 일어나는가?"

**2. 정의 (Define) — 수렴**

수집된 정보를 온톨로지로 좁힌다. Ontologist가 개념의 본질을 추출하고,
중복을 제거하며, 핵심 엔티티와 관계를 정의한다.

- 핵심 개념은 무엇인가?
- 경계 조건은 무엇인가?
- 이것의 반대는 무엇인가?
- 이것은 무엇의 부분 집합인가?

탐색과 정의 사이의 전환점(◆)은 모호성 점수(Ambiguity Score)로 결정된다.
Ambiguity ≤ 0.2가 되면 두 번째 마름모로 넘어간다.

### 두 번째 마름모: Practical Phase

**3. 창조 (Develop) — 확산**

온톨로지에서 설계로 확장한다. Seed Architect가 확인된 사양을 바탕으로
구체적인 설계와 구현 계획을 만든다.

- 아키텍처 패턴은 무엇인가?
- 어떤 기술 스택이 적합한가?
- 인터페이스는 어떻게 정의되는가?
- 데이터 흐름은 어떻게 되는가?

**4. 전달 (Deliver) — 수렴**

설계를 실행 가능한 결과물로 좁힌다. 코드, 문서, 설정, 테스트 등 구체적인
산출물을 생성한다. 이 단계는 세 번의 평가(Evaluate) 게이트를 통과해야 완료된다.

## 순환 구조 (Evolutionary Loop)

Deep mode는 단순한 선형 프로세스가 아니라 진화하는 루프다.

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Interview → Seed → Execute → Evaluate → Evolve            │
│     ↑                                          │            │
│     └──────────────────────────────────────────┘            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Interview — Socratic Questioning

Interview 단계는 Socratic Interviewer와 Ontologist가 주도한다.

- 도메인 전문가(또는 요청자)와의 대화를 통해 표면 요구사항 수집
- 각 요구사항에 대해 "왜?"를 최소 5번 반복 (5 Whys 기법)
- 숨겨진 가정과 전제를 트리 구조로 시각화
- 모순, 중복, 누락 식별
- Contrarian이 반대 가정 검증 ("반대가 사실이라면?")

**산출물**: 구조화된 질문-답변 로그, 가정 트리, 초기 온톨로지 맵

### Seed — Confirmed Specification

Seed 단계는 Seed Architect가 주도한다.

- Interview 단계의 모든 답변을 종합
- 모호성 점수 계산 (Ambiguity ≤ 0.2 확인)
- 온톨로지 수렴 검증 (Similarity ≥ 0.95)
- 확인된 사양(Confirmed Specification) 문서화
- 엔티티, 관계, 경계 조건, 제약사항 명시

**산출물**: Confirmed Specification 문서, 온톨로지 다이어그램, 경계 조건 목록

### Execute — Double Diamond

Execute 단계는 첫 번째 마름모(Socratic)가 완료된 상태에서
두 번째 마름모(Practical)를 실행한다.

- Socratic Interviewer는 질문 생산을 중단 (역할 종료)
- Seed Architect의 사양을 바탕으로 구체적 설계
- Hacker가 대안 경로 탐색 ("진짜 제약은 무엇인가?")
- Simplifier가 불필요한 복잡성 제거
- Architect가 구조적 원인 분석

**산출물**: 아키텍처 설계서, 구현 계획, 기술 사양

### Evaluate — Multi-stage Verification

Evaluate 단계는 Evaluator가 주도한다. 세 단계 검증을 수행한다:

**1단계: 내부 일관성 검증**
- 사양 내 모순이 없는가?
- 모든 용어가 일관되게 정의되었는가?
- 경계 조건이 명확한가?

**2단계: 외부 적합성 검증**
- 원래 요구사항을 충족하는가?
- 실제 환경에서 동작 가능한가?
- 모든 제약 조건이 준수되었는가?

**3단계: 메타 검증**
- "올바른 것을 만들고 있는가?" (Are we building the right thing?)
- 이 접근법이 문제 도메인에 적합한가?
- 어떤 새로운 질문이 생겼는가?

**평가 실패 시**: 피드백을 Interview 단계로 보내거나 Execute 단계로 보냄
(실패 정도에 따라 결정). 경미한 문제는 Execute로, 근본적인 재정의가 필요한
문제는 Interview로 돌아간다.

**산출물**: 검증 보고서, 통과/실패 판정, 피드백 항목

### Evolve — Reflection Loop

Evolve 단계는 전체 프로세스의 메타 인지(meta-cognition) 단계다.

- 이번 사이클에서 무엇을 배웠는가?
- 어떤 가정이 틀렸는가?
- 어떤 질문이 가장 유용했는가?
- 다음 사이클에서 무엇을 개선할 것인가?
- 지식 베이스에 무엇을 추가할 것인가?

Evolve의 결과는 다음 세대(generation)의 Interview 단계에 주입되어
프로세스 자체가 진화한다.

## 모호성 점수 (Ambiguity Score)

모호성 점수는 현재 사양이 얼마나 명확한지 정량적으로 측정한다.

### 수학적 정의

```text
Ambiguity = 1 − Σ(clarityᵢ × weightᵢ)
```

- `clarityᵢ`: i번째 차원의 명확도 (0.0 ~ 1.0)
- `weightᵢ`: i번째 차원의 가중치 (Σ weightᵢ = 1.0)
- `Ambiguity`: 최종 모호성 점수 (0.0 ~ 1.0), 낮을수록 좋음

### 차원과 가중치

| 차원 | Greenfield | Brownfield | 설명 |
|------|-----------|------------|------|
| 목표 명확성 (Goal clarity) | 40% | 35% | "무엇을 만들 것인가?"가 얼마나 명확한가 |
| 제약 명확성 (Constraint clarity) | 30% | 25% | 제약 조건이 얼마나 명확히 정의되었는가 |
| 성공 기준 (Success criteria) | 30% | 25% | 성공 측정 방법이 얼마나 명확한가 |
| 컨텍스트 명확성 (Context clarity) | — | 15% | 기존 시스템과의 관계가 얼마나 명확한가 |

Brownfield 프로젝트는 기존 컨텍스트를 고려해야 하므로 Context clarity 차원이
추가된다. 이에 따라 다른 차원의 가중치가 상대적으로 낮아진다.

### 임계치

**Ambiguity ≤ 0.2** : 통과. 두 번째 마름모(Practical Phase)로 진행 가능.
**Ambiguity ≤ 0.4** : 보류. 추가 질문과 정의가 필요함.
**Ambiguity > 0.4** : 실패. 첫 번째 마름모(Socratic Phase)를 재실행해야 함.

### 계산 예시

Greenfield 프로젝트의 예:
- Goal clarity = 0.8 (목표는 대략 명확하나 세부사항이 모호)
- Constraint clarity = 0.6 (몇몇 제약이 아직 발견되지 않음)
- Success criteria = 0.3 (성공 기준이 거의 정의되지 않음)

```text
Ambiguity = 1 − (0.8 × 0.4 + 0.6 × 0.3 + 0.3 × 0.3)
         = 1 − (0.32 + 0.18 + 0.09)
         = 1 − 0.59
         = 0.41
```

Ambiguity = 0.41 > 0.2 → Socratic Phase 재실행 필요. 성공 기준을 먼저 명확히 해야 함.

명확화 후:
- Goal clarity = 0.95
- Constraint clarity = 0.90
- Success criteria = 0.85

```text
Ambiguity = 1 − (0.95 × 0.4 + 0.90 × 0.3 + 0.85 × 0.3)
         = 1 − (0.38 + 0.27 + 0.255)
         = 1 − 0.905
         = 0.095
```

Ambiguity = 0.095 ≤ 0.2 → 통과. Practical Phase로 진행 가능.

## 온톨로지 수렴 (Ontology Convergence)

온톨로지 수렴은 여러 참여자가 동일한 개념적 모델에 도달했는지 확인하는 과정이다.

### 유사도 계산

```text
Similarity = 0.5 × name_overlap + 0.3 × type_match + 0.2 × exact_match
```

- `name_overlap`: 두 온톨로지에서 동일하거나 유사한 이름을 가진 개념의 비율
  (0.0 ~ 1.0). 유사성은 어간(stem) 일치, 동의어(synonym) 일치 포함.
- `type_match`: 두 온톨로지에서 동일한 타입/카테고리로 분류된 개념의 비율
  (0.0 ~ 1.0). 예: 둘 다 "User"를 "Entity"로 분류하면 일치.
- `exact_match`: 두 온톨로지에서 완전히 동일한 정의를 가진 개념의 비율
  (0.0 ~ 1.0). 이름, 타입, 속성, 관계가 모두 일치해야 함.

### 가중치 해석

- **name_overlap (0.5)**: 가장 높은 가중치. 개념의 이름과 명명 규칙이
  일치하는 것이 가장 기본적인 수렴 조건이다. 이름이 다르면 같은 개념을
  가리키고 있어도 의사소통 오류가 발생한다.
- **type_match (0.3)**: 두 번째 가중치. 같은 이름이라도 다른 타입으로
  분류되면 개념적 차이가 있음을 의미한다. 예: "User"가 Entity인가 Role인가.
- **exact_match (0.2)**: 가장 낮은 가중치. 완전한 일치는 이상적이지만,
  모든 개념에서 달성하기 어렵다. 부분적 차이는 허용되되, 핵심 개념에서의
  차이는 문제가 된다.

### 임계치

**Similarity ≥ 0.95** : 수렴 완료. 온톨로지가 충분히 일관됨.
**Similarity ≥ 0.80** : 부분 수렴. 차이가 있는 개념에 대해 추가 질문 필요.
**Similarity < 0.80** : 수렴 실패. Socratic Phase 재실행.

### 병리적 패턴 (Pathological Patterns)

온톨로지 수렴 과정에서 자주 관찰되는 네 가지 병리적 패턴:

**1. 정체 (Stagnation)**

유사도가 특정 값에서 더 이상 증가하지 않는 현상. 일반적으로 0.6 ~ 0.8 사이에서
발생한다.

- 원인: 근본적인 개념적 차이가 해소되지 않음
- 해결: Contrarian을 투입해 양측의 가정을 근본부터 재검토
- 징후: 세 번의 반복 동안 유사도 변화가 0.01 미만

**2. 진동 (Oscillation)**

유사도가 증가와 감소를 반복하며 수렴하지 않는 현상.

- 원인: 참여자들이 서로 다른 온톨로지를 번갈아 수용
- 해결: Researcher를 투입해 외부 참조(reference) 도입
- 징후: 유사도가 0.7 ↔ 0.85 사이를 3회 이상 진동

**3. 반복적 피드백 (Repetitive Feedback)**

동일한 질문과 답변이 순환하는 현상.

- 원인: 진전 없이 같은 논의를 반복
- 해결: Architect가 구조적 재정의(structural reframing) 제안
- 징후: 새로운 개념이나 질문이 3회 반복 동안 등장하지 않음

**4. 하드 캡 (Hard Cap)**

온톨로지의 표현력 한계로 인해 더 이상 정밀해질 수 없는 현상.

- 원인: 사용 중인 언어, 프레임워크, 또는 도메인 모델의 표현력 한계
- 해결: Simplifier가 현재 한계 내에서 최선의 모델을 찾도록 유도
- 징후: 유사도가 0.90 ~ 0.94에서 정체되며,
       추가 질문이 "그건 표현할 방법이 없어요"로 이어짐

## 아홉 개의 사고 (Nine Thinking Agents)

Deep mode는 아홉 개의 서로 다른 사고 방식을 가진 에이전트 persona로 구성된다.
각 에이전트는 특정 역할과 핵심 질문을 가지며, 전체 프로세스의 한 측면을 담당한다.

| Agent | 역할 | 핵심 질문 |
|-------|------|-----------|
| **Socratic Interviewer** | 질문만 하고 절대 만들지 않는다 | "내가 지금 무엇을 가정하고 있지?" |
| **Ontologist** | 증상 너머 본질을 찾는다 | "이것은 정확히 무엇인가?" |
| **Seed Architect** | 대화에서 사양을 굳힌다 | "모호성이 사라졌는가?" |
| **Evaluator** | 3단계 검증을 수행한다 | "우리가 올바른 것을 만들고 있는가?" |
| **Contrarian** | 모든 가정에 의문을 제기한다 | "반대가 사실이라면?" |
| **Hacker** | 대안 경로를 찾는다 | "진짜 제약은 무엇인가?" |
| **Simplifier** | 복잡성을 제거한다 | "동작하는 가장 단순한 것은?" |
| **Researcher** | 코딩 전에 조사한다 | "증거가 무엇인가?" |
| **Architect** | 구조적 원인을 찾는다 | "정말 이렇게 밖에 없을까?" |

### 각 에이전트의 활동 영역

**Socratic Interviewer**
- 활동: Interview 단계 전체
- 출력: 질문, 답변 로그
- 제약: 절대 해결책을 제안하지 않음. 오직 질문만.
- 판단 기준: "이 질문이 더 깊은 질문을 열었는가?"

**Ontologist**
- 활동: Interview 후반 ~ Seed 초반
- 출력: 온톨로지 맵, 개념 정의, 관계 다이어그램
- 제약: 구현 세부사항을 논의하지 않음. 오직 개념과 본질만.
- 판단 기준: "이 개념의 충분 조건과 필요 조건이 모두 정의되었는가?"

**Seed Architect**
- 활동: Seed 단계
- 출력: Confirmed Specification 문서
- 제약: Socratic Interviewer와 Ontologist의 결과물만 사용.
      자신의 가정을 추가하지 않음.
- 판단 기준: "모호성 점수가 임계치 이하인가?"

**Evaluator**
- 활동: Evaluate 단계
- 출력: 검증 보고서, 통과/실패 판정
- 제약: 건설적인 비판만. 단순한 부정은 금지.
- 판단 기준: "이것이 실제 환경에서 실패하지 않을 것이라는 증거가 있는가?"

**Contrarian**
- 활동: Interview 단계, Seed 검증 시점
- 출력: 반대 가정, 경계 사례, 무효화 시나리오
- 제약: 생산적인 반대만. 단순한 논쟁은 금지.
- 판단 기준: "이 가정이 거짓이라면 무엇이 달라지는가?"

**Hacker**
- 활동: Execute 단계 초반
- 출력: 대안 설계, 우회 경로, 재정의된 제약 목록
- 제약: 현실적인 대안만. 공상 과학 금지.
- 판단 기준: "진짜 제약을 우회하는 방법이 있는가?"

**Simplifier**
- 활동: Execute 단계 전반
- 출력: 단순화된 설계, 불필요한 기능 제거 목록
- 제약: 핵심 요구사항을 훼손하지 않는 단순화만.
- 판단 기준: "이것을 제거해도 여전히 문제가 해결되는가?"

**Researcher**
- 활동: Execute 단계, 특히 기술 결정 시점
- 출력: 조사 보고서, 벤치마크, 사례 연구
- 제약: 일차 자료(primary source)만 인용. 추측 금지.
- 판단 기준: "이 주장을 뒷받침하는 증거가 충분한가?"

**Architect**
- 활동: Execute 단계, Evolve 단계
- 출력: 구조 분석, 리팩토링 제안, 장기 로드맵
- 제약: 현재 컨텍스트에 적합한 조언만.
- 판단 기준: "이 결정이 6개월 후에도 합리적일 것인가?"

## 워크플로우 통합

### Phase 0: Domain Interview (Socratic Interviewer + Ontologist)

Harness 워크플로우의 Phase 0은 deep mode의 Interview 단계에 직접 대응한다.

1. 사용자가 요청을 제출한다 (예: "챗봇을 만들어줘")
2. Socratic Interviewer가 질문을 생성한다
3. Ontologist가 답변을 분석하고 온톨로지 맵을 업데이트한다
4. Contrarian이 가정을 검증한다
5. 모호성 점수가 계산된다
6. Ambiguity ≤ 0.2가 될 때까지 2-5 반복
7. 온톨로지 수렴이 확인되면 Phase 1으로 진행

### Ambiguity Scoring이 Phase 1 진입을 게이트한다

모호성 점수는 Phase 0과 Phase 1 사이의 게이트 역할을 한다.

```text
Phase 0 (Interview)
  │
  ▼
Ambiguity ≤ 0.2? ── 아니오 ──→ Socratic Interviewer 재투입
  │
  예
  ▼
Phase 1 (Seed + Execute)
```

이 게이트는 요구사항이 충분히 명확해지기 전에 구현을 시작하는 것을 방지한다.

### Evaluation 피드백 루프가 Harness 품질을 개선한다

Evaluate 단계의 결과는 harness 생성물의 품질을 개선하는 데 사용된다.

- **3단계 평가 실패 → Phase 0 재실행**: 온톨로지 자체가 잘못되었거나
  불완전함을 의미. Socratic Interviewer가 새로운 질문으로 복귀.
- **2단계 평가 실패 → Phase 2 재실행**: 설계나 구현에 문제가 있음을 의미.
  Execute 단계로 복귀.
- **1단계 평가 실패 → 로컬 수정**: 내부 일관성 문제. 최소한의 수정으로 해결.

### /harness:deep 명령어

Deep mode는 harness 시스템 내에서 다음과 같이 호출된다:

```text
/harness:deep <요청>
```

예시:
```text
/harness:deep "REST API용 인증 모듈을 만들어줘"
```

이 명령어는 다음을 트리거한다:

1. Phase 0 강제 활성화 (Ambiguity 점수 무조건 계산)
2. Socratic Interviewer 자동 기동
3. 모든 Nine Thinking Agents 할당
4. 모호성 게이트를 통과할 때까지 Phase 0 반복
5. 통과 후 자동으로 Phase 1-4 진행
6. 모든 결과물에 온톨로지 맵과 모호성 점수 포함

### Deep mode 진입 조건

Deep mode가 항상 필요한 것은 아니다. 다음 조건 중 하나라도 해당되면
deep mode 진입이 권장된다:

- 요청이 5문장 이상으로 복잡한 경우
- 도메인이 익숙하지 않은 경우
- 여러 이해관계자가 관련된 경우
- 기존 시스템과의 통합이 필요한 경우
- "사실은..." 또는 "조건이 있어요" 같은 표현이 등장하는 경우
- 이전에 유사한 작업이 실패한 경우

반대로, 다음과 같은 경우 deep mode 없이 직접 실행 가능하다:

- 단순하고 반복적인 작업 (파일 생성, 설정 변경 등)
- 완전히 문서화된 정형화된 프로세스
- 긴급 수정 (hotfix)

### Deep mode 생략 시 위험

Deep mode를 생략하면 다음과 같은 위험이 증가한다:

- 잘못된 가정에 기반한 구현 (50% 이상)
- 중간에 요구사항 변경으로 인한 재작업 (30%)
- 생성된 에이전트 팀이 실제 문제와 미스매치 (40%)
- 불완전한 경계 조건 처리로 인한 버그 (60%)

이 수치는 Ouroboros 프로젝트의 경험적 데이터를 기반으로 하며,
프로젝트 복잡도에 따라 변동될 수 있다.
